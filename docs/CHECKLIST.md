## Phase 2c - Storage reliability (added 24/08/2026, after the long incident)

Mitigations applied under pressure that need to be reviewed, plus the gaps the incident exposed. See the History entries for 18-24/08.

- [x] Switch the OPNsense NICs from `e1000` to `virtio` (28 MB/s at 196% CPU → 66 MB/s at 36%)
- [x] Give the USB pool disk its own I/O thread (`aio=threads,iothread=1`), so a stalled request no longer freezes the whole VM
- [x] Raise TrueNAS RAM from 6144 to 8192 MB (VM 100 was already powered off, and is now leaving the hypervisor altogether)
- [x] Disable the guest watchdog's reset at the hypervisor (`-global ICH9-LPC.noreboot=true`) - it was destroying data and evidence
- [x] **Raise `timeo` to 600 and `retrans` to 5** on the three NFS lines in `fstab` - still `soft`, so the host can never lock up as it did on 10/08, but tolerant enough to stop truncating files mid-write
- [ ] **Return `sync=standard` on `tank_test/media`** once the storage can sustain it - `sync=disabled` is a mitigation, not a fix, and trades up to five seconds of acknowledged writes on a crash
- [ ] **Re-enable the watchdog** once the platform is stable - it has real value on a headless NAS that is not stalling three times a day
- [x] **Enable SSH on TrueNAS**, restricted to the Trusted zone - not having it cost the gentle recovery path on three separate nights, leaving no option but killing the VM
- [x] Audit the OPNsense rules after the interface reassignment: the household redirects (SMB `:445`, TrueNAS UI `:8443`), the WireGuard NAT on 51820, outbound from Trusted, and the `10.10.10.10 → WAN net` rule
- [x] Decide what to do about the **global IPv6 address** the firewall picked up on WAN via DHCPv6 - the whole segmentation is IPv4 and IPv6 does not use NAT, so this is a path no rule currently covers
- [x] Verify large copies by comparing file sizes between source and destination - `cp` finishing without an error is no longer sufficient proof on this system

## Phase 2d - Operating within the current hardware (decided 24/08/2026)

**This is the phase that replaced Phase 3 as the active one.** No hardware is being bought for now, and that decision has a consequence that has to be stated rather than left implicit: **the mitigations from Phase 2c are no longer temporary, they are the operating configuration.** Their costs are accepted knowingly:

| Mitigation | Accepted cost |
|---|---|
| `sync=disabled` on `tank_test/media` | Up to ~5 seconds of acknowledged writes lost on a crash or power cut. Media only, never `nextcloud` |
| Watchdog reset disabled | A stalled TrueNAS stays stalled until someone intervenes, instead of resetting itself. Deliberate: a reset mid-write truncates files silently, which is worse |
| `timeo=600,retrans=5` | A stalled mount takes minutes to return an error instead of seconds. Deliberate: it is what stops files being truncated mid-write |

The underlying fact does not change: a single mechanical disk, in a USB dock, serving NFS to five clients, with no redundancy and no separate log device. **What changes is the response to it: manage the load rather than grow the hardware.**

- [ ] **Monitoring, brought forward from Phase 5** - the single highest-value item now. The failure of 18-24/08 ran for six days before being noticed, precisely because the `soft` mounts of 10/08 turned it into a silent, self-recovering degradation. Running with permanent mitigations on fragile storage without alerting is the actual risk. Costs almost nothing to run
- [ ] Set `recordsize=1M` on `tank_test/media` - free, and better suited to large sequential files than the 128K default. Applies only to newly written data
- [x] **Give the free USB 3 port to the Ethernet adapter rather than the backup SSD** (24/08/2026) - the SSD on USB 2 caps at roughly 40 MB/s, but the backup reads from the mechanical disk over NFS at around 66 MB/s, so it is limited by the source either way and the gain would be small and unfelt at 04:00. The adapter sat in the path of everything the household does against the homelab. Note the USB 3 move brought no gain by itself: the real bottleneck was elsewhere, see the next item
- [x] **Move the firewall WAN cable from the powerline adapter to the gigabit switch** (24/08/2026) - the powerline adapter's RJ45 ports are **100 Mbit/s**, and `ethtool` showed the link negotiated at exactly that. The same read test went from **11.3 MB/s to 109.4 MB/s**, close to the 118 MB/s the onboard NIC reaches. Physical separation preserved: still a separate cable, NIC and switch port
- [ ] **Stagger the heavy jobs** so they do not overlap: the 04:00 backup, Jellyfin library scans, *arr imports and qBittorrent rechecks. Concurrency is what pushes this disk over the edge, not any single task
- [ ] **Back up the Nextcloud database** - the files are covered daily but the database is not, and a restore without it hands back files with no Nextcloud around them. A `mysqldump` into the existing backup script. Free, and the most serious gap in the current backup design
- [ ] Re-measure after the above, and only then decide whether `sync` can return to `standard`

## Phase 3 - Storage / RAID (conditional: requires hardware, not scheduled)

**Not planned work.** This remains the correct engineering answer to the incident of 18-24/08, and it is recorded here so that the reasoning is not lost, but nothing else in this document treats it as a prerequisite.

**Triggers that would justify revisiting it**: the media library growing past the 1TB disk; a second failure that the Phase 2d measures do not contain; SMART starting to report reallocated sectors; or simply wanting the redundancy, given that today a single disk failure loses the entire pool.

- [ ] 2x identical NAS HDDs (4TB or 6TB) in a ZFS mirror - the only thing that turns ZFS's checksums from *detection* into *repair*
- [ ] Prefer SATA over the USB dock if the chassis allows it - the JMicron bridge was cleared under test, but it remains a link in the chain that server hardware would not have
- [ ] A small SSD as a **SLOG** (ZFS intent log) - the specific fix that would let `sync=standard` return without the latency that caused the write timeouts

### Phase 4b - Kubernetes

## Phase 5 - Monitoring and alerting (brought forward 24/08/2026)

See [TOOLING.md §3](TOOLING.md#3-monitoring-and-alerting---slack).

**Repositioned twice by the decision of 24/08.** It was planned as a workload on k3s, which put it behind a RAM upgrade that is no longer scheduled, so it is **re-targeted at a small LXC with Docker** - Uptime Kuma needs a couple of hundred MB and nothing else. And it moved **up** in priority rather than down: running permanently mitigated workarounds on storage known to be fragile, with no alerting, is the largest remaining risk in the project.

- [x] Create the `#homelab-alerts` channel on Slack + an Incoming Webhook - done 31/08/2026 and **verified by stopping a real container**, not just by the test button. The webhook URL is a secret and lives in `SECRETS.md`. Note the trap: existing monitors do not inherit a new notification, so "apply to all existing monitors" has to be ticked or the alerts silently reach nobody
- [x] Install Uptime Kuma in its own LXC (not k3s) - **LXC 108 `monitor`**, 512MB, flat network `192.168.1.91:3001`, Docker Compose, created 31/08/2026. Deliberately on VLAN 1 rather than Management: to alert, it must reach the internet, and from the flat network it does so through the switch and the router **without depending on the firewall** it is supposed to be watching. Wired to Slack the same day, so the chain from detection to phone is complete
- [x] **The check that would have caught the 18-24/08 failure**: a periodic *real* read of an NFS mount (an `ls` with a timeout), not a port check. `showmount` answered throughout that week while `nfsd` was dead, and a TCP check on 2049 answered too - both would have reported green for six days
- [x] Alert on **host load average and available memory** - the cascade always announced itself the same way, with load climbing in a straight line for twenty minutes before anything became unusable. Thresholds: load above 20 or under 800MB available stops the heartbeat. Both would have fired on 25/08, when the host reached load 1633 with 741MB available
- [ ] Add **I/O pressure** (`/proc/pressure/io`) to the same check - `full` above 50% for a sustained period is the earliest signal of all, earlier than load
- [ ] Alert on TrueNAS restarting unexpectedly - it rebooted itself six times on 24/08 and nobody noticed until the boot list was read by chance
- [ ] Cover the **scheduled jobs** (04:00 backup, ZFS scrub) with Uptime Kuma **Push** monitors - catches the failure an uptime check structurally cannot see: a job that *fails* produces an error, a job that *stops running* produces nothing at all. **Healthchecks.io was dropped for this on 31/08/2026**, see `TOOLING.md` §3: Uptime Kuma already implements the dead man's switch, and adding a Django plus Postgres stack to watch two cron jobs contradicts the rule that the watcher must be simpler than what it watches
- [ ] (Later) Prometheus + Grafana for history and graphs - useful, but it is the alerting that has the value here, not the dashboards

- 12/08/2026: **permissions on files written over NFS**, discovered when media could not be deleted or moved over SMB from Windows. Cause: the export's `Mapall` treats every NFS request as root, so everything written through it (including everything Sonarr and Radarr import) is owned by root with mode `644` - readable but not writable by the `rui` SMB user. `Mapall` cannot simply be changed to `rui`, because that is what fixed Nextcloud's `chown` failure in July and changing it would break it again. Solved on the permissions side rather than the ownership side: group ownership plus group write applied recursively from the TrueNAS permissions editor, the **setgid** bit on the directories (`chmod g+s`) so new files inherit the directory's group, and `UMASK=002` in the *arr containers so new files are created `664` rather than `644`. The three together are needed - setgid alone gives the right group but no write permission.
- 12/08/2026: **local bind mounts into unprivileged containers need `chown 100000:100000`**. After moving downloads to the local SSD, every torrent showed as "errored". Cause: unprivileged containers shift UIDs by 100000, so a folder created by the host's root appears inside as `nobody` with no write access. The symptom is misleading because `ls` on the host shows a perfectly ordinary folder. **This does not apply to NFS mounts**, where TrueNAS's `Mapall` handles the translation - which is exactly why it catches you out.
- 18-24/08/2026: **The long incident: NFS stalling, cascading host load, and five separate causes**. The most drawn-out failure of the project, spread over six days, with four of my own hypotheses ruled out along the way. **Symptoms**: load averages of 274, 165 and 62 on a 6-core machine, NFS unresponsive, dozens of processes stuck in `D`, `pct`/`qm` hanging, the Proxmox web UI down, and TrueNAS rebooting itself (six times on 24/08 alone). **What made it hard is that everything measured came back healthy**: SMART `PASSED`, the pool `ONLINE` with zero errors, the network at 0.6ms, the disk at **0% utilisation**, and TrueNAS itself logging normally, serving SMB authentications and running cron on schedule throughout. **The layered diagnosis**, in the order the pieces fell: (1) `showmount -e` answered while any real `ls` hung, which separates `mountd`, that reads export configuration, from `nfsd`, that needs the data; (2) TrueNAS's operating system lives on a qcow2 on the local SSD while the pool lives on the USB disk, which is why logs, cron and SMB kept working while storage was frozen; (3) the VM console showed `txg_sync blocked for more than 120 seconds` with the four `nfsd` threads blocked behind it, so everything above ZFS was a victim, not a cause; (4) `rcu_preempt detected stalls` with `0 ticks this GP` meant the guest's own vCPUs were frozen, not merely slow. **Five causes, all real, all contributing**: **(a)** the OPNsense VM had **`e1000` emulated NICs**, and since the TrueNAS migration to Trusted on 11/08 every byte of storage traffic was routed through it; it saturated both cores at 196% to deliver 28 MB/s, and switching to `virtio` with `queues=2` gave 66 MB/s at 36%, roughly thirteen times the efficiency per byte. **(b)** the USB disk passthrough had **no dedicated I/O thread and used `io_uring`**, so its I/O ran on QEMU's main loop; a stalled request there freezes the entire VM, timers and vCPUs included, which is exactly what the RCU stalls showed. Fixed with `aio=threads,iothread=1`. **(c)** with `sync=standard`, every NFS commit went through the **ZIL on the same single mechanical disk**, writing each block twice with a head seek between them. **(d)** the mount options `timeo=150,retrans=3`, set on 10/08 to make the `soft` mounts fail fast, meant the client gave up after about 45 seconds and returned `Input/output error` **in the middle of writes**, leaving files that looked complete but were not: one episode ended at 5 MB of 166. **(e)** the guest's **iTCO watchdog**, with a 30 second timeout, was resetting the VM whenever a stall outlasted it, which destroyed data, corrupted the journal, and erased the very evidence needed to diagnose the stall.
- 18-24/08/2026: **the wrong hypotheses, and what ruled each one out**. Worth recording because the eliminations were as useful as the findings. **Memory exhaustion** (TrueNAS at 6GB with no swap): plausible for days, and the reason RAM was raised to 8GB, but the journal showed no OOM at any point. **The JMicron USB bridge** (`152d:8561`, a known-problematic family): ruled out by writing 3GB of incompressible data directly to the pool at 91.3 MB/s with no error. **CPU starvation of the guest**: ruled out by the host's own CPU pressure sitting at 0-2%, and by noticing that load made almost entirely of `D`-state processes measures waiting, not competition for the processor. **The *arr stack as the cause**: it was a reliable trigger, but a plain `cp` of a single file reproduced the failure with every container stopped, which demoted it from cause to workload.
- 18-24/08/2026: **the most instructive mistake: a test that tested nothing**. Early on, `dd if=/dev/zero of=... bs=1M count=2000 oflag=sync` was run inside TrueNAS, completed at 54 MB/s with no errors, and was taken as proof that the storage was healthy. It proved nothing: the dataset has `compression=lz4`, and ZFS stores all-zero blocks as holes, so nothing of consequence ever reached the platter. That false negative sent the investigation toward the network for several hours. **Any throughput test against a compressed dataset must use incompressible data** (`/dev/urandom`, or real media files); the same trap invalidates `dd`-based benchmarks on any modern filesystem with compression enabled.
- 18-24/08/2026: **method lessons from this incident**. **An open port is not a working service**: `mountd` answering `showmount` while `nfsd` was dead misled the diagnosis twice. **A disk at 0% utilisation while everything blocks is starved, not saturated**: the block layer is idle precisely because nothing above it is submitting work, and reading that as "the disk is fine" cost eleven days. **`cp` finishing without an error stopped being proof**: verification by comparing file sizes between source and destination is now mandatory after any large copy on this system, and it is what caught the 5 MB episode. **And the fix of 10/08 hid the problem it did not solve**: switching to `soft` mounts saved the host from locking up, but turned every subsequent stall into a silent, self-recovering degradation, which is why five days of failures went completely unnoticed until they became severe. That is the argument for Phase 5 in a single sentence.
- 24/08/2026: **changes applied during the incident**, all of them measured rather than assumed. OPNsense NICs switched from `e1000` to `virtio` with `queues=2` - note that this changes the interface names inside OPNsense from `em*` to `vtnet*` and requires reassignment on the console, during which `opt1` and `opt2` lost their IP configuration and had to be set again by hand; export the firewall configuration **before** attempting this. TrueNAS's `scsi1` (the USB pool disk) given `aio=threads,iothread=1`. TrueNAS RAM raised from 6144 to 8192 MB, with VM 100 kept powered off to stay inside the host's budget. `sync=disabled` set on `tank_test/media` as a temporary mitigation (**not** applied to `nextcloud`, where losing recently acknowledged writes is not acceptable). The guest watchdog's reset disabled at the hypervisor level with `-global ICH9-LPC.noreboot=true`, on the reasoning that a watchdog exists to press a reset button nobody can reach, and on a VM the hypervisor is always that button - here it was only destroying data and evidence.
- 24/08/2026: **firewall audit after the NIC switch, done by diff rather than by eye**. OPNsense keeps a configuration history with diffs (System → Configuration → History), which turned a "read every rule and hope" job into two minutes of reading what actually changed. The console reassignment had **deleted the `opt1` (TRUSTED) and `opt2` (MGMT) interface definitions outright**, descriptions included, which is why they came back as generic `OPT1`/`OPT2` with no addresses. It had also silently switched the **WAN from static to DHCP and enabled DHCPv6**, which is where the unexplained global IPv6 address came from. **The important finding was a negative one**: neither diff touched the `<filter>` or `<nat>` sections. OPNsense rules reference interfaces by logical name (`opt1`, `opt2`) rather than by device, so they were orphaned for the eleven minutes those interfaces did not exist and reattached themselves the moment the names came back. The whole network policy survived intact, with nothing to restore. **Verified by testing rather than by reading**, which is the standing lesson of this week: TrueNAS reaching the internet from Trusted (21ms to 1.1.1.1, which also proves the restored static WAN), SMB and the TrueNAS interface from the household network, and the VPN from mobile data reaching both Jellyfin and the Proxmox panel - that last one exercising the router's port forward, the NAT on 51820 and the `10.10.10.10 → WAN net` rule in a single test. All four passed. WAN put back to static `192.168.1.95/24` with IPv6 set to **None**, which closes the exposure noted the day before.
- 24/08/2026: **VM 100 leaves the hypervisor**, and the plan corrected on a point I had overstated. Writing "k3s waits for the RAM" was too coarse: k3s exists for edge and IoT, and a single-node control plane fits in 2 to 3GB. What genuinely needs memory is what runs *on* it - migrating Jellyfin and Nextcloud (both stacks running in parallel during the cutover, for the same services with one more layer underneath) and the `kube-prometheus-stack`, which wants 2 to 4GB by itself. With VM 100 gone, a small k3s VM fits in the current 16GB, so **Phase 4b splits again**: the cluster and the code-driven deployment loop, which is where the learning and portfolio value sits, proceed on today's hardware; only the migrations and the full metrics stack wait. Removing VM 100 also closes the question of its network zone, open since 28/07/2026, and it frees nothing in RAM today because it was already powered off - what it removes is an 8GB allocation reserved for something that might restart, and the caveat that shadowed every sizing decision.
- 24/08/2026: **the development environment moves to a dedicated physical machine**, connected by Ethernet to the TL-SG608E. Recorded now as a forward reference, with the design deliberately deferred. One correction to the entry above it: closing the network-zone question because VM 100 is leaving was right for VM 100, but the question itself did not disappear - it moved to a machine where the constraints are different. A guest gets a zone with a `tag=` on a virtual NIC and nothing else; a physical host needs either an untagged port on VLAN 1, staying outside the homelab, or a tagged port plus VLAN configuration on its own interface. And the switch is already doing double duty, carrying the trunk to the OptiPlex alongside untagged household traffic, so the decision touches more than one thing. Reopened as its own item rather than left closed.
- 24/08/2026: **household-to-homelab transfers were capped at 11 MB/s by a 100 Mbit port, and it took three wrong guesses to find it**. Symptom: reading a file from the TrueNAS SMB share over `192.168.1.95` ran at 11.3 MB/s, while `iperf3` from the same PC to the same physical machine on `192.168.1.206` gave 118 MB/s. Same source, same destination host, ten times the difference. **First guess, wrong**: the backup SSD and the Ethernet adapter were both on USB 2, so the adapter was moved to USB 3 - no change at all, because 11 MB/s is far below what even USB 2 delivers. **Second guess, wrong**: the powerline medium, which would have shown irregular numbers rather than a figure that steady. **Third guess, wrong**: the VLAN crossing needing the router - it does not, because the PC and the firewall's WAN leg are in the same subnet, and the VLAN 1 to VLAN 20 hop happens inside the OptiPlex between two virtual interfaces on the same bridge, at memory speed. **The answer took one command**: `ethtool` reported `Speed: 100Mb/s`. The adapter's cable was plugged into the powerline adapter, whose RJ45 ports are Fast Ethernet, and 11.3 MB/s is simply a saturated 100 Mbit link. Moving that cable to a free port on the gigabit switch gave **109.4 MB/s**, and the same 1145 MB file went from 101 seconds to 10.5. **The lesson repeats the one from the storage incident**: check what a link actually negotiated before replacing anything around it. `ethtool` would have answered on the first minute instead of the fortieth. It also corrected a claim in `NETWORK.md` that had been sitting there since 02/08 - that traffic between the PC and the homelab never touched the powerline. It was true only for the host's own flat-network address, and false for every service reached through the firewall's redirects, which is to say all of them.
- 31/08/2026: **monitoring installed, and the `ip6=manual` practice found to be wrong**. LXC 108 `monitor` created (Debian 12, unprivileged+nesting, 1 core, 512MB, `192.168.1.91`), running Uptime Kuma under Docker Compose. Placed on the **flat network rather than Management**, deliberately: to raise an alert it has to reach the internet, and from VLAN 1 it does so through the switch and the router without depending on the firewall it is meant to be watching. The same reasoning kept it out of k3s - **whatever does the watching should be simpler than what it watches**. Given `startup order=3`, right after the firewall and *before* the services, because the system fell over on 23/08 during exactly that window and a monitor that starts last never sees the most interesting minute of the day. **The two checks that matter are Push monitors, not port checks**: a script on the Proxmox host (`/usr/local/bin/monitor-push.sh`, cron every minute under `flock`) does a real `ls` on the three NFS mounts with a hard timeout, and only calls the push URL if all three answer - silence is the alarm. It reports the actual duration of those reads as the response time, which gives something never available before: **the degradation is visible before the failure**. A second Push monitor does the same for load average and available memory. This design exists because of the specific way the August incident hid itself: port 2049 accepted TCP connections and `showmount` answered for six days while `nfsd` was dead, so any conventional check would have reported green throughout. **And while creating the container, a documented practice turned out to be false**: the note from 10/08 claims `ip6=manual` stops containers picking up global IPv6 addresses. It does not - it disables DHCPv6, but **SLAAC** still works, and the container configured itself from the router's advertisements. Checking the others found LXCs 101, 104, 105 and 107 all holding public IPv6 addresses, on a network whose segmentation is entirely IPv4 and where IPv6 uses no NAT. Fixed on all five with `net.ipv6.conf.all.disable_ipv6=1` via `/etc/sysctl.d/`, which is what actually stops it.
